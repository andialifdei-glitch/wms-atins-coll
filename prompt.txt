# A. KONTEKS DAN TUJUAN

Web-portal ini merupakan bagian dari ekosistem WMS Atin’s Coll. Aplikasi Android WMS sebelumnya sudah memiliki pengembangan integrasi cek ongkir RajaOngkir. Namun, jangan berasumsi bahwa struktur kode, endpoint, autentikasi, konfigurasi, atau implementasi Android dapat langsung dipakai oleh web.

Tugas pertama adalah memeriksa repository web yang sedang terbuka, mengidentifikasi teknologi dan arsitektur aktualnya, lalu menentukan implementasi yang sesuai.

8. Menghindari bug yang pernah terjadi pada integrasi Android WMS.

Fitur saat ini hanya untuk **cek ongkir**. Jangan membangun fitur pembuatan AWB, booking pengiriman, pickup, cetak label ekspedisi, atau tracking resi karena belum diminta.

# J. KONTRAK DATA FRONTEND DAN BACKEND

Buat kontrak request/response internal yang konsisten dengan framework web yang digunakan.

Request internal setidaknya memuat:
- ID asal yang valid.
- ID tujuan yang valid.
- Berat dalam satuan yang sudah ditetapkan.
- Provider/kurir yang diminta.
- Konteks transaksi jika berasal dari SO, tanpa mengirim data sensitif yang tidak diperlukan.

Response internal sebaiknya memiliki status yang jelas, misalnya:
- `AVAILABLE`: layanan ditemukan.
- `TARGET_SERVICE_NOT_RETURNED`: respons valid, tetapi layanan yang diminta tidak ditemukan.
- `API_ERROR`: request ke API gagal.
- `INVALID_RESPONSE`: format respons tidak valid.
- `VALIDATION_ERROR`: input pengguna tidak valid.
- `CONFIGURATION_ERROR`: konfigurasi API belum tersedia.

Nama status boleh disesuaikan dengan konvensi project, tetapi semantik harus tetap jelas.

Untuk setiap hasil ongkir, pertahankan informasi yang benar-benar tersedia:
- Provider.
- Kode layanan asli.
- Nama layanan asli.
- Tarif.
- Estimasi.
- Deskripsi tambahan bila tersedia.

Jangan menganggap semua provider mempunyai struktur respons identik. Buat parser berdasarkan struktur yang benar-benar dikembalikan API.

# K. BUG YANG PERNAH TERJADI DAN PENCEGAHANNYA

Bug berikut pernah dilaporkan pada pengembangan integrasi Android WMS. Jadikan kasus ini sebagai skenario pengujian dan pemeriksaan. Jangan menganggap akar masalahnya sudah pasti sebelum membaca log dan source code.

## Bug 1 — Semua destinasi menampilkan tarif yang sama

Gejala:
Destinasi Lampung, Karawang, dan Bandung pernah menghasilkan tarif yang sama, sekitar Rp22.000.

Dugaan penyebab yang perlu diverifikasi:
- ID destinasi tidak ikut berubah ketika pengguna memilih alamat baru.
- UI mengirim nama wilayah tetapi backend mengharapkan ID destinasi.
- Mapping ID wilayah keliru.
- State tujuan lama masih dipakai.
- Cache menggunakan key yang tidak menyertakan ID destinasi.
- Backend mengabaikan parameter tujuan atau memakai nilai default.
- Respons sebelumnya ditampilkan kembali setelah request baru.

Solusi yang harus diterapkan:
1. Telusuri nilai tujuan dari UI sampai request API.
2. Log ID asal, ID tujuan, berat, dan provider secara aman.
3. Pastikan ID tujuan sesuai dengan wilayah yang dipilih.
4. Pastikan request body memakai nama parameter yang sesuai dokumentasi aktif.
5. Pastikan cache key mencakup parameter yang memengaruhi hasil, minimal asal, tujuan, berat, dan provider/layanan.
6. Jangan memakai satu nilai destinasi default untuk semua pilihan.
7. Pastikan respons hanya ditampilkan untuk request yang sesuai dengan state terbaru.
8. Buat tes untuk minimal tiga destinasi berbeda.
9. Jika tarif memang kebetulan sama dari API, jangan mengubahnya; verifikasi raw response dan parameter request terlebih dahulu.

## Bug 2 — Desa Jayakerta, Karawang tidak ditemukan

Gejala:
Pencarian destinasi pernah gagal menemukan Jayakerta, Karawang.

Solusi yang harus diterapkan:
1. Periksa apakah endpoint pencarian destinasi yang digunakan benar untuk API aktif.
2. Periksa query pencarian, normalisasi spasi, kapitalisasi, dan karakter khusus.
3. Periksa apakah API menyediakan wilayah pada tingkat desa/kelurahan atau memerlukan tingkat wilayah yang berbeda.
4. Periksa relasi ID kabupaten, kecamatan, dan desa jika API menyediakan hierarki tersebut.
5. Jangan menebak atau membuat ID wilayah sendiri.
6. Jangan menyatakan wilayah tidak didukung hanya karena satu query gagal.
7. Jika perlu, cari menggunakan nama wilayah induk atau query alternatif yang sah, kemudian validasi hasilnya berdasarkan ID dan nama lengkap.
8. Jika data memang tidak tersedia di API, tampilkan penjelasan dan jangan mengirim ID palsu ke endpoint ongkir.
9. Tambahkan tes untuk hasil kosong, query alternatif, dan pemilihan wilayah induk yang benar.

## Bug 3 — Cloud Functions mengembalikan NOT_FOUND

Gejala:
Endpoint Cloud Functions pernah mengembalikan `NOT_FOUND`.

Penyebab yang perlu diperiksa:
- URL function salah.
- Nama function berbeda dengan nama yang dipanggil frontend.
- Region function berbeda dengan region pada URL.
- Function belum dideploy atau deployment gagal.
- Frontend memanggil endpoint lama.
- URL hosting atau rewrite rule tidak sesuai.
- Endpoint dipanggil dengan method atau path yang tidak sesuai.

Solusi:
1. Periksa nama function yang benar-benar dideploy.
2. Periksa region deployment.
3. Cocokkan URL frontend dengan URL aktual dari output deployment.
4. Periksa log deployment dan log function.
5. Pastikan method HTTP dan route sesuai implementasi.
6. Gunakan konfigurasi environment untuk URL bila diperlukan.
7. Jangan mengganti endpoint secara acak atau mengubah konfigurasi Firebase lain tanpa alasan.
8. Jangan mengubah `firestore.rules`.
9. Buat health check yang aman untuk memastikan backend dapat dijangkau tanpa mengungkap secret.

Jangan menganggap semua error `NOT_FOUND` berasal dari URL. Periksa respons lengkap dan log untuk membedakan route tidak ada, resource tidak ditemukan, dan kesalahan dari upstream API.

## Bug 4 — TOO_MANY_REGISTRATIONS

Gejala:
Error `TOO_MANY_REGISTRATIONS` pernah muncul selama pengembangan.

Jangan langsung menyimpulkan bahwa penyebabnya adalah kuota request ongkir. Error ini harus ditelusuri dari sumber yang benar.

Solusi:
1. Catat layanan/endpoint yang mengeluarkan error.
2. Periksa apakah error berasal dari Firebase Authentication, Cloud Functions, RajaOngkir, atau layanan lain.
3. Periksa status HTTP, response body, waktu kejadian, dan log server tanpa mencatat secret.
4. Jika berasal dari alur registrasi Firebase, periksa frekuensi pembuatan akun, konfigurasi Authentication, dan batas layanan terkait.
5. Jika berasal dari API atau backend, ikuti makna error yang sebenarnya berdasarkan dokumentasi layanan tersebut.
6. Jangan membuat akun berulang untuk menguji koneksi.
7. Jangan melakukan retry tanpa batas.
8. Untuk pencarian wilayah, terapkan debounce dan cache agar ketikan pengguna tidak memicu request berlebihan.
9. Untuk kalkulasi ongkir, cegah klik berulang saat request masih berjalan.
10. Jika ditemukan rate limit, tampilkan pesan dan terapkan retry terbatas sesuai ketentuan layanan.

Jangan mengganti error ini dengan pesan sukses palsu.

## Bug 5 — Layanan JagoPack atau SPX-Hemat tidak ditemukan

Gejala:
Respons diagnostik yang pernah diuji tidak mengembalikan layanan Lion JagoPack atau SPX-Hemat.

Solusi:
1. Ambil dan periksa raw response API.
2. Cocokkan kode dan nama layanan asli.
3. Jangan memetakan `REGPACK` menjadi JagoPack.
4. Jangan memetakan `SPX Standard` menjadi SPX-Hemat.
5. Gunakan nama layanan yang benar-benar dikembalikan API.
6. Bedakan layanan yang tidak dikembalikan dari API error.
7. Jangan mengarang tarif atau estimasi.
8. Pertahankan daftar UI yang telah disepakati: Wahana Ekonomis, Lion REGPACK, SPX Standard, dan Kurir Toko.

## Bug 6 — Respons API tidak valid atau tarif/ETD kosong

Solusi:
- Periksa HTTP status dan struktur JSON.
- Jangan hanya memeriksa apakah body respons tidak kosong.
- Validasi keberadaan array/data layanan sesuai kontrak API.
- Tangani tarif kosong, estimasi `-`, dan deskripsi yang tidak tersedia tanpa crash.
- Jangan mengubah ETD yang tidak diketahui menjadi angka perkiraan.
- Jangan menampilkan tarif nol sebagai ongkir gratis kecuali API secara eksplisit mengembalikan nilai yang memang berarti nol.
- Simpan raw response diagnostik di server hanya jika diperlukan, dengan penyamaran data sensitif dan pembatasan akses.

# ADDENDUM MASTER PROMPT — HEMAT KUOTA API DAN PENGATURAN TOKO

Terapkan ketentuan tambahan berikut sebagai bagian wajib dari integrasi cek ongkir RajaOngkir pada web-portal WMS Atin’s Coll.

Jangan mengulang pembangunan dari awal jika implementasi sebelumnya sudah tersedia. Periksa hasil pekerjaan yang ada dan lakukan perubahan incremental pada bagian yang diperlukan.

## 1. BATASAN KUOTA RAJAONGKIR

Kuota API RajaOngkir yang tersedia adalah 100 hit per hari. Karena itu, pengembangan dan pengujian harus sangat hemat request.

Ketentuan wajib:

1. Jangan melakukan load test atau pengujian berulang terhadap API asli.
2. Jangan memanggil API setiap kali pengguna mengetik karakter pada kolom pencarian.
3. Gunakan debounce, tetapi jangan menganggap debounce saja cukup untuk menghemat kuota.
4. Hindari request duplikat dengan parameter yang sama.
5. Cache data wilayah dan hasil pemeriksaan yang sesuai, dengan masa berlaku yang wajar.
6. Cache hasil ongkir harus menggunakan key yang mempertimbangkan seluruh parameter yang memengaruhi hasil, seperti asal, tujuan, berat, dan kurir.
7. Jangan menggunakan cache hasil ongkir jika parameter request berubah.
8. Jangan memanggil ulang API hanya untuk menampilkan kembali hasil yang sudah tersimpan dan masih layak digunakan.
9. Jangan otomatis memeriksa ongkir ketika halaman dibuka, ketika state UI berubah, atau ketika pengguna berpindah menu.
10. Pemeriksaan ongkir hanya dilakukan saat memang dibutuhkan, misalnya ketika pengguna menekan tombol “Cek Ongkir”.
11. Cegah klik ganda selama request masih berjalan.
12. Jangan menerapkan retry otomatis tanpa batas.
13. Jangan menguji semua provider dan semua destinasi secara massal.
14. Jangan melakukan request API asli hanya untuk memverifikasi perubahan tampilan UI.
15. Untuk unit test dan sebagian besar integration test, gunakan mock response atau fixture yang disanitasi. Mock hanya untuk pengujian, tidak boleh menjadi hasil ongkir produksi.
16. Pengujian API asli cukup dilakukan sesedikit mungkin untuk membuktikan konfigurasi dan alur utama berfungsi.

Sebelum menjalankan pengujian API asli, periksa apakah hasil pengujian yang diperlukan sudah tersedia dari request sebelumnya. Gunakan hasil tersebut bila masih relevan dan tidak perlu memanggil API lagi.

### Batas pengujian yang disarankan

- Unit test: gunakan mock; tidak memakai kuota API asli.
- Build, lint, dan type-check: tidak memakai kuota API RajaOngkir.
- Tes backend dengan fixture: tidak memakai kuota API RajaOngkir.
- Tes koneksi API key: hanya satu request ringan yang sah menurut dokumentasi aktif, jika memungkinkan.
- Tes cek ongkir end-to-end: lakukan satu request dengan rute valid setelah konfigurasi disetujui, lalu gunakan hasil yang sama untuk memeriksa rendering UI.
- Request tambahan hanya dilakukan jika request sebelumnya gagal dan ada alasan jelas untuk mengulanginya.

Angka di atas adalah batas proses pengujian yang disarankan, bukan jaminan bahwa setiap endpoint hanya dihitung satu hit oleh penyedia API.

### Perlindungan tambahan terhadap kuota

Jika memungkinkan berdasarkan arsitektur yang sudah ada:
- Buat cache server-side agar beberapa pengguna tidak mengulang request identik secara bersamaan.
- Terapkan deduplikasi request yang sedang berjalan.
- Berikan indikator ketika hasil berasal dari cache.
- Catat jumlah request upstream yang benar-benar dilakukan oleh backend, tanpa mencatat API key.
- Jangan menampilkan perkiraan sisa kuota sebagai angka pasti jika informasi tersebut tidak diberikan oleh API.

Jangan membuat endpoint tambahan yang memanggil RajaOngkir hanya untuk mengukur kuota atau memeriksa status layanan jika tidak diperlukan.

Sebelum mengimplementasikan, periksa source code Android yang tersedia atau implementasi terkait untuk memahami alur yang digunakan. Jika source Android tidak tersedia di repository web, ikuti perilaku yang dijelaskan dalam spesifikasi ini. Jangan mengklaim telah menyalin implementasi Android secara persis tanpa memeriksanya.

## 3. ALUR PERUBAHAN API KEY — WAJIB DIIKUTI

Implementasikan alur berikut dengan jelas.

### Langkah 1 — Input API key baru

ROOT_ADMIN memasukkan API key baru pada halaman Pengaturan Toko.

Pada tahap ini:
- API key baru hanya berada dalam state sementara untuk proses pengujian.
- API key aktif yang sedang dipakai aplikasi tidak boleh ditimpa.
- Jangan langsung menyimpan API key baru ke konfigurasi aktif.
- Jangan menampilkan API key lengkap setelah proses penyimpanan.
- Jangan mengirim API key ke browser selain yang benar-benar diperlukan untuk proses pengujian melalui mekanisme aman. Utamakan pengiriman langsung ke endpoint backend yang dilindungi HTTPS, lalu backend yang melakukan pengujian ke RajaOngkir.

### Langkah 2 — Tombol “Uji Koneksi”

Saat ROOT_ADMIN menekan “Uji Koneksi”:

1. Backend memvalidasi autentikasi dan role ROOT_ADMIN.
2. Backend menerima key sementara melalui koneksi HTTPS.
3. Backend melakukan satu request pengujian yang sah dan ringan menggunakan API key baru.
4. Backend memeriksa HTTP status, format respons, dan indikasi keberhasilan autentikasi.
5. Hasil pengujian dikembalikan ke UI.
6. API key aktif yang lama tetap dipertahankan sampai proses konfirmasi dan penyimpanan berhasil.

Jangan menggunakan request yang mahal atau melakukan beberapa request sekaligus untuk menguji satu API key.

Jika tidak tersedia endpoint khusus untuk uji koneksi, gunakan satu endpoint ringan yang memang sah menurut dokumentasi aktif. Jelaskan bahwa hasil pengujian membuktikan akses endpoint yang diuji, bukan jaminan bahwa setiap layanan pengiriman tersedia.

### Langkah 3 — Jika API key berhasil diuji

Jika hasil pengujian menyatakan API dapat bekerja:

- Tampilkan pesan keberhasilan yang jelas.
- Tampilkan dialog konfirmasi dengan tombol **OK**.
- Contoh pesan: “Koneksi RajaOngkir berhasil. API key baru dapat digunakan. Tekan OK untuk melanjutkan ke konfirmasi penyimpanan.”
- Setelah ROOT_ADMIN menekan OK, tutup dialog hasil dan tandai API key sementara sebagai `TEST_SUCCESS`.
- Aktifkan tombol **“Konfirmasi dan Simpan API Key”**.
- Jangan mengganti API key aktif secara otomatis hanya karena pengujian berhasil.

Tombol OK pada dialog hasil pengujian hanya mengakui pesan dan melanjutkan alur. Tombol tersebut bukan pengganti tombol penyimpanan akhir.

### Langkah 4 — Jika API key gagal diuji

Jika request pengujian gagal karena API key salah, tidak memiliki izin, atau autentikasi ditolak:

- Tampilkan pesan kegagalan yang jelas.
- Berikan informasi aman yang membantu diagnosis, seperti kategori error atau HTTP status.
- Jangan tampilkan secret atau informasi sensitif.
- Jangan menimpa API key aktif.
- Jangan menghapus API key aktif yang lama.
- Jangan menandai key baru sebagai `TEST_SUCCESS`.
- Tombol **“Konfirmasi dan Simpan API Key” harus tetap disabled**.
- Pengguna dapat memperbaiki input lalu menguji ulang jika memang diperlukan.
- Jangan melakukan retry otomatis berkali-kali.

Jika kegagalan disebabkan gangguan jaringan, timeout, atau server error, perlakukan sebagai hasil pengujian yang tidak berhasil. Jangan mengizinkan penyimpanan melalui alur normal hanya karena error tersebut mungkin bersifat sementara.

### Langkah 5 — Tombol “Konfirmasi dan Simpan API Key”

Tombol ini berada di bawah bagian input dan hasil pengujian.

Aturan tombol:
- Disabled secara default.
- Hanya ROOT_ADMIN yang dapat menggunakannya.
- Hanya aktif jika API key sementara yang saat ini dimasukkan telah lulus pengujian.
- Jika input API key berubah setelah pengujian, hasil pengujian lama langsung dianggap tidak berlaku dan tombol kembali disabled.
- Jika pengujian berlangsung, tombol disabled.
- Jika pengujian gagal, tombol disabled.
- Jika API key kosong, tombol disabled.
- Jika hasil pengujian tidak diketahui, tombol disabled.

Saat tombol diklik:
1. Backend memvalidasi ulang autentikasi dan role ROOT_ADMIN.
2. Backend memastikan pengujian berhasil untuk API key yang sama dengan yang akan disimpan.
3. Backend menolak penyimpanan jika key yang dikonfirmasi berbeda dari key yang diuji.
4. Backend menyimpan API key baru secara aman.
5. Backend memverifikasi bahwa proses penyimpanan berhasil tanpa menampilkan secret.
6. Setelah penyimpanan berhasil, konfigurasi aktif diperbarui.
7. UI menampilkan notifikasi bahwa API key baru berhasil disimpan.
8. API key lama hanya diganti setelah penyimpanan baru benar-benar berhasil.

Jangan hanya mengandalkan state tombol frontend. Validasi status pengujian dan hak akses harus dilakukan kembali di backend.

Gunakan mekanisme pengikatan pengujian dengan key yang sama, misalnya token pengujian sementara atau fingerprint/hash yang aman, agar hasil uji key A tidak dapat digunakan untuk menyimpan key B. Jangan menyimpan key plaintext di log atau basis data sementara yang tidak aman.

Jika penyimpanan gagal, pertahankan konfigurasi aktif yang lama dan tampilkan pesan kegagalan.

## 4. STATE UI YANG DISARANKAN

Sesuaikan dengan pola framework web, tetapi pastikan semua kondisi berikut tertangani:

- `IDLE`: belum diuji.
- `TESTING`: pengujian sedang berlangsung.
- `TEST_SUCCESS`: key yang saat ini dimasukkan telah lulus pengujian.
- `TEST_FAILED`: pengujian gagal.
- `SAVING`: penyimpanan sedang berlangsung.
- `SAVE_SUCCESS`: key baru berhasil disimpan.
- `SAVE_FAILED`: penyimpanan gagal.

Ketentuan penting:
- Perubahan input key membatalkan `TEST_SUCCESS`.
- Tombol konfirmasi penyimpanan hanya aktif pada `TEST_SUCCESS`.
- Jangan menganggap key tersimpan sebelum backend menyatakan penyimpanan berhasil.
- Jangan menyimpan state `TEST_SUCCESS` secara permanen di browser agar dapat digunakan kembali tanpa pengujian baru.
- Jika halaman di-refresh atau sesi berubah, jangan menganggap key baru telah diuji.
- Hindari race condition ketika pengguna mengganti key saat request pengujian masih berlangsung.

## 5. PENGUJIAN FITUR PENGATURAN TANPA MEMBOROSKAN KUOTA

Gunakan mock untuk menguji seluruh alur UI:
- Input key.
- Pengujian sukses.
- Dialog OK.
- Tombol konfirmasi menjadi aktif.
- Input key berubah dan tombol kembali disabled.
- Pengujian gagal dan tombol tetap disabled.
- Penyimpanan sukses.
- Penyimpanan gagal dan key aktif lama tetap berlaku.
- Pengguna bukan ROOT_ADMIN tidak dapat mengakses endpoint pengaturan.

Mock tidak boleh dipakai sebagai bukti bahwa API key asli valid.

Untuk tes API asli, cukup gunakan satu request yang sah untuk menguji key sementara. Jika berhasil, lanjutkan dengan konfirmasi UI dan simpan key. Jangan mengulang request yang sama hanya untuk memeriksa tampilan tombol.

## 6. TES REGRESI DAN LAPORAN

Pastikan:
- Kuota tidak dipakai untuk unit test dan tes UI.
- Tidak ada request otomatis berulang saat halaman dibuka.
- Tidak ada request pencarian wilayah pada setiap karakter tanpa debounce.
- API key aktif tidak berubah ketika pengujian gagal.
- API key aktif baru berubah setelah konfirmasi dan penyimpanan berhasil.
- Tombol konfirmasi disabled pada seluruh kondisi selain hasil uji yang valid untuk key yang sama.
- Alamat asal hanya berubah setelah disimpan dengan data wilayah yang valid.
- Snapshot ongkir SO lama tidak dihitung ulang.
- Aturan COD tidak berubah.
- `firestore.rules` dan sistem autentikasi tidak diubah tanpa instruksi eksplisit.
- Tidak ada secret di frontend, log, atau laporan.

Dalam laporan akhir, jelaskan:
1. Cara penghematan kuota diterapkan.
2. Jumlah request API asli yang benar-benar dilakukan selama pengujian.
3. Endpoint yang dipanggil saat uji API key.
4. Perilaku saat uji sukses, uji gagal, dan penyimpanan gagal.
5. File yang diubah.
6. Hasil build dan tes.
7. Hal yang belum terverifikasi.

Jangan mengeklaim bahwa kuota pasti aman hanya karena debounce diterapkan. Jelaskan mekanisme nyata yang mencegah request berulang dan hasil pengujian yang benar-benar dilakukan.
